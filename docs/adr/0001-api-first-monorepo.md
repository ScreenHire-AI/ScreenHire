# ADR-0001: API-first architecture in a single monorepo

- **Status:** Accepted (2026-10-18)
- **Deciders:** Owner

## Context
ScreenHire needs a public API for integrations from day one (GoHire has none — a competitive gap), plus several web
surfaces (marketing site, candidate careers pages, recruiter dashboard) and background processing (integrity analysis,
job-board sync, email).

## Decision
- A **standalone HTTP API** is the only way any client — our own dashboard included — reads or writes data. The
  dashboard consumes the API exactly as a third-party integrator would.
- **One monorepo** holds all apps and shared packages:

```
apps/
  api/          ASP.NET Core public REST API + webhooks
  worker/       .NET background workers (outbox, integrity pipeline, distribution, email)
  careers/      Astro SSR — tenant careers pages, apply form, questionnaire
  marketing/    Astro SSG — screenhire marketing site, blog, SEO content
  dashboard/    Recruiter SPA (framework: ADR-0006)
  apphost/      .NET Aspire orchestration for local dev (pending ADR-0008)
packages/
  telemetry/    framework-free TS behavioural-telemetry module
  api-client/   TS client generated from the OpenAPI spec
  ui/           shared design tokens + components (ADR-0009)
src/            .NET class libraries (Domain, Application, Infrastructure, Integrity, Distribution, Workflow)
tests/
docs/
```

- The **OpenAPI 3.1 document** generated by the API is the contract; TS clients and JSON Schemas (workflow definitions)
  are generated from it in CI.

## Consequences
- Public API quality is guaranteed by dogfooding.
- Two toolchains (dotnet + pnpm) in one repo; CI must cache both.
- Contract drift is caught at build time by regenerating the client and type-checking the frontends.
