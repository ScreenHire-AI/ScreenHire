# Add a migration

The schema is Postgres, generated by EF Core from `ScreenHireDbContext` and the configurations in
`src/ScreenHire.Infrastructure/Persistence/Configurations`. In Development the API applies migrations at startup
(`DevelopmentDataSeeder.MigrateAndSeedAsync`), so a migration you add runs the next time the AppHost starts, in
`pnpm dev` and in every integration test.

**Migration name:** $ARGUMENTS (PascalCase, says what changes: `AddCandidates`, `AddJobClosedReason`. Never
`Update1` or `Fix`.)

## 1. Change the model

- Entities live in `src/ScreenHire.Domain` and stay free of EF attributes. Mapping goes in an
  `IEntityTypeConfiguration<T>` in `Persistence/Configurations`, picked up by `ApplyConfigurationsFromAssembly`.
- Add a `DbSet<T>` to `ScreenHireDbContext` for an aggregate root.
- Names are snake_case automatically (`UseScreenHireConventions()`): never call `ToTable` or `HasColumnName` to get
  snake_case by hand.
- Strings get `HasMaxLength`. Enums are text: `HasConversion<string>().HasMaxLength(20)`. Money is
  `HasPrecision(12, 2)`. Times are `DateTimeOffset` (`.claude/rules/utc-timestamps.md`).
- Every foreign key gets an explicit `OnDelete` and every common query path an index.

### Tenant-owned tables

A table that holds one organization's data (jobs, candidates, applications, templates, notes) needs all of this:

- [ ] an `OrganizationId` column, a foreign key to `organizations`, and indexes that start with it
      (`HasIndex(x => new { x.OrganizationId, x.Slug }).IsUnique()` in `JobConfiguration.cs` is the pattern);
- [ ] uniqueness scoped to the organization, never global (two tenants may both have a `backend-engineer` job);
- [ ] once tenancy is on `main` (look for a tenant query filter in `ScreenHireDbContext.OnModelCreating`): the named
      query filter for the entity, and in the migration, raw SQL that enables row-level security and adds the
      policy and grants, following the earliest migration on `main` that does so:
      `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`, `FORCE ROW LEVEL SECURITY`, a policy comparing
      `organization_id` with `current_setting('app.tenant_id', true)::uuid`, and grants to the application role.
      Before tenancy lands, there is no policy to copy: every query filters by organization explicitly.

Run the `tenant-isolation-guard` agent on the change before you finish.

## 2. Generate it

```
dotnet tool restore
dotnet ef migrations add <Name> --project src/ScreenHire.Infrastructure --startup-project src/ScreenHire.Infrastructure --output-dir Persistence/Migrations
```

This writes `<timestamp>_<Name>.cs`, `<timestamp>_<Name>.Designer.cs` and updates
`ScreenHireDbContextModelSnapshot.cs`. It does not connect to a database (`DesignTimeDbContextFactory` builds the
model offline).

To undo a migration that is not merged yet, delete its two files and restore the snapshot
(`git checkout -- src/ScreenHire.Infrastructure/Persistence/Migrations/ScreenHireDbContextModelSnapshot.cs`, or
re-run `migrations add` after fixing the model). Do not use `dotnet ef migrations remove`: it connects to whatever
Postgres answers on `localhost:5432`, which on a shared machine is not yours, and `--force` would revert that
database.

## 3. Review the SQL

```
dotnet ef migrations script <PreviousMigration> <Name> --project src/ScreenHire.Infrastructure --startup-project src/ScreenHire.Infrastructure
```

`<PreviousMigration>` is the name before yours in `Persistence/Migrations` (`0` means an empty database). Read the SQL
as the person who will run it against production data:

- column types are what you meant (`timestamp with time zone`, `character varying(n)`, `numeric(12,2)`, `uuid`);
- a new `NOT NULL` column on an existing table has a default or a backfill, or the table is new;
- no `DROP COLUMN` or `DROP TABLE` of data that is still needed; a rename shows as `RENAME`, not drop and add;
- indexes on large tables are worth their write cost.

Edit the generated `Up` and `Down` only to add what EF cannot express (RLS, a backfill, `CREATE EXTENSION`). Keep
`Down` working.

Then confirm the snapshot matches the model:

```
dotnet ef migrations has-pending-model-changes --project src/ScreenHire.Infrastructure --startup-project src/ScreenHire.Infrastructure
```

## 4. Prove it

- `pnpm verify:dotnet`.
- An integration test that exercises the new table through the API (the AppHost applies the migration on start).
  For a tenant table, include a test that another organization's rows are invisible.
- Run the `migration-safety` agent on the diff.

## Rules that do not bend

- **Never edit a migration that is on `main`.** Fix forward with a new migration.
- **Conflicts with `main`:** follow `.claude/rules/integration-conflicts.md`. Take `main`'s snapshot, delete this
  branch's migration files, finish the merge, and re-create the migration with the same name, so it holds only this
  branch's change.
- One migration per task where possible. If you changed the model twice on an unmerged branch, delete your
  migration and generate one again.
